PROJECT: ModelGuard AI
Premium Frontend Design & Development Specification
1. YOUR ROLE

Act as a world-class SaaS product designer, senior frontend engineer, motion designer, and UX architect.

Build a complete, polished, production-quality frontend for ModelGuard AI, an intelligent Machine Learning model monitoring platform.

The product helps developers deploy machine learning models, monitor their behavior, detect changes in incoming data, identify potential reliability problems, and understand what needs attention.

The interface must be visually distinctive, intuitive, responsive, accessible, and technically functional.

Do not create a generic admin dashboard.

Create a memorable product experience that feels like a combination of:

A premium AI observability platform.
A futuristic scientific monitoring laboratory.
A beautiful, editorial SaaS application.
An intelligent digital command center.

The result should be visually impressive enough for a portfolio presentation, LinkedIn post, project demonstration, and technical interview.

2. PRODUCT VISION

Product name: ModelGuard AI

Tagline: "Your models deserve a second pair of eyes."

Alternative headline:
"Know when your AI starts changing."

Supporting description:

"Monitor your machine learning models, understand changing data patterns, and investigate potential reliability issues before they go unnoticed."

Primary goal:

Help users understand the current state of their machine learning models without requiring advanced knowledge of machine learning or cloud infrastructure.

A non-technical user should be able to open the dashboard and understand these questions within seconds:

Is my model working?
How many predictions has it made?
Is anything unusual happening?
What does the warning mean?
What should I do next?

Every major design decision must support these five questions.

3. UNIQUE VISUAL IDENTITY
Design concept: "The Living Intelligence Observatory"

The central visual metaphor is a living observatory that continuously watches machine learning models.

Represent each registered model as an intelligent entity with a recognizable visual identity.

A healthy model appears calm, stable, and balanced.

A model experiencing unusual input patterns displays subtle visual changes.

A model requiring attention becomes visually highlighted, with a clear explanation and recommended action.

Use animation to communicate meaningful state changes rather than decorating the interface randomly.

Color palette

Create a sophisticated light-first interface.

Primary background:
Warm ivory: #F7F7F2

Main surface:
Pure white: #FFFFFF

Primary text:

Borders:

Use gradients sparingly.

Preferred gradient:
Indigo to violet with a subtle blue highlight.

Avoid:

Excessive neon colors.
Pure black backgrounds throughout the application.
Overused purple gradients on every card.
Excessive glassmorphism.
Glowing borders around every component.
Unreadable low-contrast gray text.
Rainbow-colored charts.

The product should feel elegant, calm, intelligent, and trustworthy.

Typography

Use:

A distinctive display font such as Manrope for large headings.

Create a clear hierarchy:

Large editorial page titles.
Medium-weight section headings.
Compact labels.
Comfortable body text.
Tabular numbers for metrics.

Keep important information readable at normal desktop viewing distances.

Layout personality

Use:

Generous whitespace.
Asymmetric but balanced compositions.
Rounded cards with approximately 16–24px corner radii.
Thin borders.
Subtle, natural shadows.
Small illustrated details.
Carefully controlled motion.
Consistent spacing.

Avoid the standard layout where every section consists of four identical metric cards followed by generic charts.

Make the composition visually interesting while maintaining usability.

The central model symbol fades in.
Orbital rings appear sequentially.
Small activity nodes emerge.
The model status appears.
Metric values transition into place.

Keep the entire sequence subtle and reasonably fast.

Animation 2: Prediction flow

When the user clicks "Run prediction":

The input card transitions into a processing state.
A subtle visual signal moves toward the result panel.
The result appears when the API responds.
The measured latency is displayed.

If the API fails, show a helpful error state rather than a fabricated prediction.

Animation 3: Drift visualization

When a monitoring evaluation completes:

Reference and incoming distributions appear.
The chart transitions smoothly to the latest values.
A warning indicator appears if the evaluation identifies a significant change.
The explanation panel expands.

The animation must reflect actual results.

Animation 4: Alert appearance

When a new alert is received:

Show a subtle entrance transition.
Update the alert count.
Add a clear text label.
Avoid flashing or aggressive shaking.
Animation 5: Navigation

Use smooth transitions for:

Sidebar selection.
Page entry.
Tabs.
Dialogs.
Expandable panels.
Dropdown menus.

Keep navigation responsive.

Performance requirements
Prefer transform and opacity animations.
Avoid expensive continuous animations across the entire screen.
Pause decorative motion when the tab is hidden where practical.
Respect the user's reduced-motion preference.
Do not animate every card independently.
Avoid scroll hijacking and unnecessary parallax.

The design must remain attractive even when animations are disabled.

18. DATA AND BACKEND INTEGRATION

The frontend must be designed to integrate with a FastAPI backend.

Create a dedicated API service layer.

Example files:

src/
components/
pages/
layouts/
hooks/
services/
api.ts
models.ts
predictions.ts
monitoring.ts
alerts.ts
types/
utils/

Keep API logic separate from UI components.

Use TypeScript interfaces for API request and response objects.

Suggested endpoints:

GET /health

GET /models

POST /models/register

GET /models/{model_id}

POST /predict

GET /predictions

GET /monitoring/{model_id}/drift

POST /monitoring/{model_id}/evaluate

GET /alerts

GET /alerts/{alert_id}

The exact endpoints may be adapted to the backend implementation.

Do not assume an endpoint exists until it has been implemented.

Use the backend's actual response schema.

Create loading, empty, disconnected, and error states for every data-dependent page.

If an API request fails:

Explain what happened.
Offer a retry action.
Preserve user-entered form data where appropriate.
Avoid replacing failed requests with invented results.

Use environment variables for the backend URL.

Example:

VITE_API_BASE_URL=http://localhost:8000

Provide an .env.example file.

Never place secret keys in Vite environment variables because browser-exposed variables are not secret.
